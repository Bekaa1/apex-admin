# Виджет поддержки Apex

## Подключение и маршруты

`src/routes.tsx` подключает один `ChatRouteLayout`. Компонент виджета загружается лениво из `src/chat/widget/ChatWidget.tsx`. Правило видимости находится в `src/chat/widget/routePolicy.ts`: требуется `handle.publicChat` у публичной ветки маршрутов.

Виджет доступен на `/pricing`, `/stores`, `/how-it-works`, `/privacy`, `/offer`. Документы, открытые с `returnTo=/signup`, исключены. На `/admin/*`, `/login`, `/signup/*`, `/reset-password/*`, `/access-denied`, `/cabinet/*` и неизвестных маршрутах его нет. Корневой `/` ведёт в административный сценарий. В дереве без публичных страниц чат не монтируется.

## Конфигурация

В локальном, исключённом из Git env-файле Vite нужны:

- `VITE_CHAT_SUPABASE_URL` — `https://twnzsfsyrdnkjbkxpynl.supabase.co`;
- `VITE_CHAT_SUPABASE_PUBLISHABLE_KEY` — публичный publishable key проекта Chat либо его legacy anon key.

Значения ключей нельзя сохранять в исходниках, документации или журнале. После изменения env нужен перезапуск dev-сервера или новая production-сборка. `.env.example` содержит только названия Chat-переменных с пустыми значениями. Без конфигурации сайт работает, а открытый виджет показывает «Чат временно недоступен».

Клиент `src/lib/chatSupabase.ts` создаётся лениво, использует только `src/lib/chat.database.types.ts` и имеет `persistSession: true`, `autoRefreshToken: true`, `detectSessionInUrl: false`, `storageKey: apex-chat-auth:v1`. Основной клиент Apex и его типы независимы; Apex использует отдельный стандартный ключ SDK `sb-<project-ref>-auth-token`.

**`service_role`, secret key и приватные ключи запрещены во фронтенде, VITE-переменных и репозитории сайта.** Проверка конфигурации принимает только публичные форматы ключей. Строка-префикс `sb_secret_` встречается в коде установленного Supabase SDK для распознавания форматов; это не значение ключа. При проверке сборки нужно отличать эту библиотечную строку от настоящего секрета.

## Жизненный цикл

Единственный транспорт — `chatTransport` из `src/chat/index.ts`, реализация — `src/chat/transport.ts`. UI-контроллер `src/chat/widget/controller.ts` не вызывает Supabase напрямую.

1. Загрузка страницы и монтирование кнопки не создают анонимного пользователя. Первое открытие вызывает `initialize()`.
2. `getSession()` восстанавливает Auth Chat. Только при отсутствии сессии вызывается `signInAnonymously()`. Параллельные вызовы объединяются; Web Locks при наличии дополнительно защищает запуск между вкладками.
3. Валидный UUID `client_key` хранится в localStorage под `apex-chat-client-key:v1`. Новый `crypto.randomUUID()` нужен только при отсутствии корректного ключа. `session_id` не заменяет ключ восстановления.
4. После Auth вызывается `chat_get_or_create_session({ p_client_key })`. Полученный UUID диалога хранится в памяти.
5. Создаётся единственная INSERT-подписка `public.chat_messages` с фильтром `session_id=eq.<текущий UUID>`. История читается только после `SUBSCRIBED`.
6. `chat_list_messages` загружает до 200 последних сообщений. Старые страницы загружаются пользователем по 100, с `p_before` по времени первого загруженного сообщения.

Закрытие окна оставляет соединение активным для непрочитанных ответов. Повторное открытие не создаёт второй канал. Переход на исключённый маршрут вызывает `dispose()`: отменяются запросы, удаляется канал и Auth-listener. Возвращение восстанавливает тот же диалог через сохранённые Auth и `client_key`. Очистка localStorage, истечение или удаление анонимной учётной записи могут нарушить это восстановление.

## Отправка и повтор

Текст обрезается по краям, проверяется длина 1–4000 символов. Enter отправляет, Shift+Enter добавляет строку; IME-композиция не отправляет сообщение.

`prepareMessage()` создаёт один UUID для конкретного сообщения. `chat_send_message` получает только `p_session_id`, `p_client_message_id`, `p_body`. Прямой INSERT и передача `sender` отсутствуют. Быстрые повторные клики блокируются, автоматический повтор RPC выключен.

UI сразу показывает локальную строку «Отправляется». При ошибке сохраняется подготовленный объект, кнопка «Повторить» использует **тот же UUID**. Если ввод не изменился, повторная основная кнопка отправки также переиспользует неотправленное сообщение. После подтверждения поле очищается только если пользователь не успел набрать другой текст. RPC возвращает UUID сообщения; время и остальные канонические поля поступают из истории или Realtime.

Нормализованные сообщения проверяются по UUID, диалогу и `sender` (`visitor` либо `responder`). Дубли удаляются по серверному `id`, затем по сочетанию отправителя и ключа сообщения внутри диалога. Серверная история сортируется по `created_at` с учётом микросекунд, затем `id`. Оптимистическая строка объединяется с подтверждённой.

## Realtime и интерфейс

После переподключения история перечитывается до последней успешно загруженной контрольной точки, при необходимости несколькими ограниченными страницами. Постоянного polling нет. Старый канал удаляется при повторной инициализации; поздние события завершённого запуска игнорируются.

Посетитель отображается справа, `responder` — слева. Текст выводится обычным React-текстом с переносами строк, без HTML, Markdown и автоматических ссылок. Неизвестные ошибки заменяются безопасными сообщениями; SQL, JWT, ключи, RPC и stack trace пользователю не выводятся.

Новый ответ при закрытом окне увеличивает локальный счётчик; открытие его сбрасывает. Начальная и старая история не считаются новыми ответами. Если пользователь читает выше конца истории, появляется «Новые сообщения», позиция не сбрасывается. Escape закрывает окно, фокус возвращается на кнопку. Есть label поля, видимый фокус, умеренный `aria-live`, ru/kk/en и существующие темы Apex.

Непрочитанный счётчик, набираемый текст и неотправленный outbox хранятся в памяти, не переживают полное размонтирование/перезагрузку. После загрузки восстанавливается подтверждённая серверная история; статусы прочтения в БД не добавлены.

## Ответы внешней системы

Сайт не генерирует ответы и не содержит ИИ или операторской панели. Ответ записывает внешняя защищённая серверная система через `chat_add_response`; в виджете он появляется только из истории/Realtime как `responder`. Фронтенд этот RPC не вызывает. Служебные `_chat_*` также не вызываются. Наличие этих функций в сгенерированных типах не даёт разрешения на их клиентское использование.

## Проверка и ограничения

Локальные проверки: `npm run lint`, `npx tsc -b`, `node --test --test-reporter=spec tests/*.test.mjs`, `npm run build`, `git diff --check`. Тесты транспорта используют закрытый подменённый Supabase API; тесты виджета включают совместный сценарий с реальным транспортом. Локальный браузерный стенд `.deploy.local/chat-widget-preview` игнорируется Git и не входит в `dist`.

На 08.10.2026 обе Chat-переменные отсутствуют в разрешённой Vite-конфигурации development/production. Реальные Auth, сообщение, ответ и сетевое переподключение к Chat **не проверены**. Успешные моки и сборка не подтверждают готовность реального сервиса. Требуется настроить публичную конфигурацию и проверить Anonymous Sign-Ins (в исходном журнале они были отключены; текущая настройка не менялась и не проверялась).

После настройки выполнить одну разрешённую live-проверку: открыть публичную страницу, отправить `CHAT-SMOKE-<дата-время>`, проверить единственную строку, повторное открытие и перезагрузку с прежними Auth/key/диалогом. Один `CHAT-SMOKE-RESPONSE-<дата-время>` допустим только из защищённой серверной среды/SQL Editor с правами владельца. Если такого доступа нет, входящий live-ответ остаётся непроверенным. UUID диалога, JWT и значения ключей не записывать в журнал. Тестовые данные не удалять без отдельного задания.

Контракт истории использует только timestamp в `p_before`: совпадение времён на границе страницы не позволяет гарантировать полную выдачу средствами фронтенда. Supabase, RPC, RLS и миграции этим этапом не менялись.
