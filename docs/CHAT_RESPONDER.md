# Сервер ответов Apex Chat

Обработчик написан на Node.js/TypeScript в `server/chat`. Публичный виджет сохраняет сообщение в Supabase Chat, затем обращается к серверу ответов. Браузер не вызывает OpenRouter и не получает его ключ.

## Локальный запуск

Node.js 22.18+; используются существующие зависимости проекта.

1. В исключённом из Git `.env.chat-server.local` настроить:

   ```env
   CHAT_SUPABASE_URL=https://twnzsfsyrdnkjbkxpynl.supabase.co
   CHAT_SUPABASE_SERVICE_ROLE_KEY=
   OPENROUTER_API_KEY=
   OPENROUTER_MODEL=google/gemini-2.5-flash-lite
   APEX_PUBLIC_SUPABASE_URL=
   APEX_PUBLIC_SUPABASE_KEY=
   ```

2. `npm run dev:chat` — сервер на `127.0.0.1:8787`.
3. `npm run dev:public -- --host 127.0.0.1 --port 5173` — сайт и Vite-прокси `/api/chat/respond`.
4. Открыть чат на `http://127.0.0.1:5173/`. После изменения серверных env перезапустить обработчик.

Не добавлять серверные ключи в VITE-переменные, исходники и Git. Фронтенду нужны только публичные Chat-переменные из `docs/CHAT_WIDGET.md`.

`APEX_PUBLIC_*` — существующая публичная конфигурация Apex для чтения актуальных тарифов. Здесь принимается только publishable/anon key. Если её нет, ответы по продукту работают, но конкретные цены не называются. База знаний и её источники описаны в [CHAT_KNOWLEDGE.md](CHAT_KNOWLEDGE.md).

## Запрос и права

`POST /api/chat/respond` с Bearer JWT анонимной сессии **Chat** и JSON `{ sessionId, messageId }`.

- Сервер проверяет токен через Supabase Auth `getUser` и принадлежность `chat_sessions.visitor_user_id` этому пользователю.
- Сообщение читается по UUID, диалогу и `sender=visitor`. Браузер не передаёт историю, роль или системный промпт.
- В OpenRouter уходят расширенный промпт `server/chat/prompt.ts`, проверенная база `server/chat/knowledge.md`, текущие публичные тарифы и максимум 20 сообщений до выбранного сообщения включительно.
- Модель `google/gemini-2.5-flash-lite`, максимум 600 выходных токенов. [API OpenRouter](https://openrouter.ai/docs/api/reference/overview), [тариф модели](https://openrouter.ai/google/gemini-2.5-flash-lite/pricing).
- Ответ ограничивается 4000 Unicode-символами и записывается только через `chat_add_response`. Прямых INSERT/UPDATE нет. Клиент получает `{ ok: true }`, текст — из существующего Realtime/истории Supabase.
- Запросы без JWT, к чужому диалогу, без сохранённого сообщения посетителя и с недопустимым Origin закрыты. Origin не заменяет проверку Auth.

## Повторы и расходы

- Один процесс объединяет одновременные запросы одного сообщения; сообщения одного диалога обрабатываются последовательно.
- До генерации и записи проверяется существующий ответ с тем же `client_message_id`. RPC обеспечивает идемпотентную запись.
- Автоматических повторов платного запроса нет. При ошибке сообщение посетителя остаётся отправленным; виджет предлагает отдельно повторить запрос ответа.
- При неизвестном результате записи сервер перечитывает ответ. Готовый текст удерживается в памяти до 24 часов (до 1000 записей), чтобы ручной повтор после ошибки сохранения не вызывал новую генерацию.
- Ограничения одного процесса: 4 ожидающих/выполняющихся запроса, 10 новых запросов в минуту на Auth-пользователя. Это не распределённый лимит и не общий денежный бюджет.
- Перезапуск сбрасывает кэш и лимиты. Для нескольких реплик нужна общая очередь/блокировки: отсутствие повторной оплаты OpenRouter между процессами не гарантировано. Идемпотентность записи ответа сохраняется в существующем RPC.
- Обрабатываются только явно запрошенные сообщения; обработчик не опрашивает старые диалоги и не отвечает всем production-пользователям в фоне.

## Интерфейс

После успешного `chat_send_message` запрос ответа запускается в фоне. Можно продолжать вводить текст. Есть отдельные состояния ожидания, ошибки и ручного повтора с прежним UUID сообщения. Повтор ответа не отправляет текст посетителя в БД второй раз.

История сохраняется в Supabase и восстанавливается после reload. Незавершённые HTTP-запросы/кнопки повтора хранятся в памяти страницы; автоматического восстановления незавершённой генерации после полного закрытия страницы пока нет.

## Размещение

Для production отдельно запустить один процесс Node и настроить reverse proxy `/api/chat/respond` публичного и административного доменов на этот сервис. `CHAT_ALLOWED_ORIGINS` — точные origins через запятую, `CHAT_SERVER_PORT` и `CHAT_SERVER_HOST` — серверные настройки. Vite proxy включён для обеих сборок. Стандартные разрешённые локальные origins — localhost/127.0.0.1 на 5173 и 5174; при другом порте обновить конфигурацию.

Vite proxy работает только в dev-режиме. Загрузка одного `dist/public` не запускает обработчик.

### Production на существующем сервере

- `deploy/chat/Dockerfile` и `deploy/chat/compose.yml` запускают один процесс в контейнере `apex-chat`, без публикации порта на хост. Образ Node закреплён digest; зависимости устанавливаются из `package-lock.json`.
- Релизы сервера: `/opt/apex-chat/releases/<commit>`. Секреты хранятся отдельно в `/opt/apex-chat/runtime.env`, права `0600`, вне Git, образа и каталогов сайта. Имена переменных перечислены в разделе локального запуска.
- Запуск из каталога релиза: `CHAT_RELEASE=<commit> docker compose -f deploy/chat/compose.yml up -d --build --wait`. Для отката повторить команду из предыдущего релиза с его commit.
- Контейнер подключён к существующей сети Caddy `supabase_default`, alias `apex-chat-responder`. Перезапускается автоматически, работает непривилегированным пользователем, файловая система доступна только для чтения, логи ограничены по размеру.
- В блоках обоих доменов Caddy, до обработчика SPA: `handle /api/chat/respond { reverse_proxy apex-chat-responder:8787 }` (готовый фрагмент — `deploy/chat/chat.caddy`). Прокси сохраняет путь и Bearer-заголовок. `/health` остаётся внутренним.
- Origin в production ограничен `https://apexmedia.kz` и `https://adminapex.kz`; Auth Chat и принадлежность диалога проверяются независимо от Origin. Добавление административного домена в конфигурацию подготовлено 09.10.2026 и требует применения при следующем деплое.
- При изменении конфигурации сначала проверить Caddyfile и готовность контейнера, затем перезагрузить Caddy. Сохранить прежний Caddyfile и ссылки `current` обоих сайтов для отката.

`GET /health` сообщает наличие конфигурации, не подтверждает баланс OpenRouter или доступность Supabase. Логи содержат безопасные коды без ключей, JWT, переписки и идентификаторов клиентов.

## Общий промпт сайта и WhatsApp

Единый источник инструкций — `server/chat/prompt.ts`, база знаний — `server/chat/knowledge.md`. Экспорт `supportPrompt` используется первым системным сообщением обоих ботов без изменения текста. На сайт он попадает непосредственно из модуля; для отдельного WhatsApp-сервиса `/root/apex-ai-bot` из этой же рабочей копии генерируется `prompts/apex-agent.txt`:

```powershell
node --experimental-strip-types deploy/chat/export-whatsapp-prompt.mjs <каталог-бота>/prompts/apex-agent.txt
```

Экспорт выводит SHA-256 без содержания промпта. При обновлении инструкций или базы знаний нужно повторно экспортировать файл, собрать и перезапустить оба серверных обработчика. Перед завершением размещения сравнить SHA-256 значения `supportPrompt` в контейнере сайта и файла `/app/prompts/apex-agent.txt` в контейнере WhatsApp. Сгенерированный файл WhatsApp вручную не редактируется.

Общие инструкции описывают русский, казахский и английский языки, данные продукта, корректные обещания, историю и расшифровки аудио. Следующее системное сообщение задаёт технический контракт канала: Markdown-текст для веб-чата; JSON с `reply`, `handoff`, `language`, `tariffIds`, `lead` для WhatsApp. Передача менеджеру и четырёхчасовая пауза WhatsApp сохраняются. Веб-чат не получает несуществующую операцию вызова менеджера.

Текущие цены и история передаются отдельно. Источники тарифов остаются существующими: публичный каталог Apex у сайта и утверждённые записи собственного сервиса WhatsApp. Общий промпт не синхронизирует эти хранилища и не меняет цены. В WhatsApp суммы формирует сервер по выбранным ID; числовые параметры продукта, контакты и ссылки не считаются ценами.
