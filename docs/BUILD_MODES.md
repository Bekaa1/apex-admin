# Две сборки из main

Обновлено: 8 октября 2026 года. Сайт рекламодателя и административная панель используют общий код, типы Apex, AuthSessionProvider, дизайн-систему и переводы. В production собирается одно дерево маршрутов, выбранное Vite; адрес домена не переключает приложение.

| Назначение | Команда сборки | Выход | Preview |
| --- | --- | --- | --- |
| `apexmedia.kz` | `npm run build:public` | `dist/public` | `npm run preview:public` |
| `adminapex.kz` | `npm run build:admin` | `dist/admin` | `npm run preview:admin` |

`npm run build` собирает публичный сайт. Для одновременной разработки:

```powershell
npm run dev:public -- --port 5173 --strictPort
# В другом терминале:
npm run dev:admin -- --port 5174 --strictPort
```

Каждая сборка очищает только свой выходной каталог. Vite использует отдельные кэши `node_modules/.vite/public` и `node_modules/.vite/admin`. Зависимости и lock-файл общие; версии при интеграции не обновлялись.

## Маршруты и доступ

- `src/routes.tsx` экспортирует `@app/routes`. Alias из `vite.config.ts` выбирает `src/routes/public.tsx` либо `src/routes/admin.tsx`. TypeScript проверяет оба файла; его alias используется для определения общего типа экспорта.
- Публичная сборка: `/`, `/pricing`, `/stores`, правовые документы, регистрация, вход, восстановление пароля по email/SMS, `/cabinet/*`. «Как это работает» находится на лендинге; прежний `/how-it-works` перенаправляет на `/`. Кабинет требует RequireSession. Административные адреса здесь дают нейтральную 404.
- Административная: `/` → `/admin`, email/password-вход, административное восстановление, `/access-denied`. Всё `/admin/*`, включая неизвестные адреса и карточки, под одним RequireAdmin; очередь владельца дополнительно под RequireStoreOwner. Регистрации, лендинга и кабинета в этом дереве нет. Глобальный Chat доступен вне guards, не предоставляя прав на административные данные.
- Успех входа ведёт в `/admin` только в административном режиме; публичный вход сохраняет свой post-auth сценарий.
- ChatRouteLayout подключён один раз в корне каждой сборки. Виджет доступен на всех страницах, включая auth, кабинет, админку и 404; экземпляр сохраняется при внутренних переходах. Подробности — [CHAT_WIDGET.md](CHAT_WIDGET.md).
- Title/description создаются Vite для соответствующего приложения. Административный dev-preview остаётся DEV-only и не включается в production.
- Выбор сборки не заменяет серверные права. Auth, RPC и RLS не менялись.

## Переменные окружения

Для Apex остаются `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. Для чата в обеих сборках отдельно нужны `VITE_CHAT_SUPABASE_URL` и `VITE_CHAT_SUPABASE_PUBLISHABLE_KEY`. Используются только публичные anon/publishable ключи; серверные ключи недопустимы. Vite проксирует `/api/chat/respond` в обоих режимах; production-прокси нужно настроить на обоих доменах.

Общую локальную конфигурацию можно хранить в `.env.local`; настройки конкретной сборки — в `.env.public.local` и `.env.admin.local`. Эти файлы игнорируются Git. Существующие значения автоматически не копируются и не меняются.

**Именованные режимы читают `.env.public`/`.env.admin` и соответствующие `.local`, а не `.env.production`.** Если старое окружение хранилось только в `.env.production`, перед новой сборкой нужно передать его через окружение процесса или подходящий локальный файл. Значения ключей в документацию не переносить. После изменения env пересобрать приложение.

Без Apex-конфигурации админка закрывает доступ. Публичный лендинг остаётся доступен без видео; отсутствие Chat-конфигурации показывает безопасное сообщение в виджете.

## Следующее размещение

- Собирать нужный режим из проверенного коммита `main`.
- На `apexmedia.kz` передавать **содержимое `dist/public`**, на `adminapex.kz` — **содержимое `dist/admin`**. `index.html` должен лежать прямо в корне релиза.
- `version.json` и манифест создавать внутри выбранного подкаталога. Не архивировать общий `dist`, где могут лежать другая сборка или прежние артефакты.
- Сохранить существующие независимые каталоги релизов и current-ссылки серверов; подробности в [DEPLOYMENT.md](DEPLOYMENT.md) и [ADMIN_DEPLOYMENT.md](ADMIN_DEPLOYMENT.md).
- Merge/push сами по себе не публикуют эти приложения. В ходе данной интеграции сервер, DNS, Supabase и production не изменялись.

## Проверки

```powershell
npm run lint
npx tsc -b
node --test --test-reporter=spec tests/*.test.mjs
npm run build:public
npm run build:admin
git diff --check
```

`tests/app-build-modes.test.mjs` проверяет оба дерева, guards, восстановление пароля, конфигурацию сборок и лендинг без Supabase. Остальные тесты используют локальные моки. Реальные роли, платежи, модерация и обмен сообщениями требуют отдельной безопасной интеграционной проверки.
