### Реализация

- Переменные: `VITE_CHAT_SUPABASE_URL`, `VITE_CHAT_SUPABASE_PUBLISHABLE_KEY`. В `.env.example` значения пустые. Клиент использует тип Chat; `persistSession: true`, `autoRefreshToken: true`, `detectSessionInUrl: false`, отдельный `storageKey: apex-chat-auth:v1`. Создание клиента и соединения отложено до явного `initialize()`.
- `getSession()` переиспользует сохранённую сессию; только при её отсутствии выполняется `signInAnonymously()`. Параллельные вызовы защищены Promise, между вкладками дополнительно применяется Web Locks при наличии API. Без успешного Auth запросы диалога и Realtime не запускаются.
- `client_key` создаётся через `crypto.randomUUID()` и хранится в `localStorage` под `apex-chat-client-key:v1`. Валидный UUID переиспользуется после перезагрузки/повторной инициализации. Ошибка localStorage останавливает инициализацию. `session_id` остаётся только в оперативном состоянии.
- Подключены только `chat_get_or_create_session`, `chat_list_messages`, `chat_send_message`. Прямой записи в таблицы, служебных вызовов и фронтенд-вызова `chat_add_response` нет.
- История нормализуется в `id`, `sessionId`, `sender`, `body`, `clientMessageId`, `createdAt`. Допустимы только `visitor` и `responder`. Посторонний диалог, неизвестный отправитель и некорректная строка дают безопасную ошибку формата.
- `prepareMessage()` создаёт один неизменяемый объект с UUID и обрезанным текстом длиной 1–4000 символов. Повторять нужно `send()` с тем же объектом. Двойной вызов делит один RPC. `sender` не отправляется. UUID из ответа отправки не подменяется искусственной строкой: канонические данные приходят из истории или Realtime.
- На всех RPC отключён SDK retry, установлен тайм-аут и отмена запросов. Автоматической повторной отправки сообщения нет. Ошибка чтения после подтверждённой записи сохраняется отдельно от успешного результата отправки.
- Порядок запуска: Auth → получение UUID диалога → INSERT-подписка `public.chat_messages`, `session_id=eq.<UUID>` → `SUBSCRIBED` → история. В установленном SDK используется `postgres_changes_options.wait: true`, чтобы дождаться подтверждения Postgres-подписки.
- Единое хранилище объединяет сообщения по `id`, затем по `sender + client_message_id` внутри диалога. Ответ с тем же ключом посетителя сохраняется отдельно. Сортировка учитывает микросекунды `created_at`, затем `id`.
- После переподключения история дочитывается страницами по 200 до предыдущей успешной контрольной точки. Исправлен случай первоначально пустого диалога с более чем 200 сообщениями за время обрыва. Старые страницы доступны через `loadOlder()`; постоянного polling нет.
- `dispose()` отменяет запросы, удаляет канал и Auth-listener; поздние ответы не меняют состояние. Повторная инициализация закрывает предыдущий канал. При выходе из Chat или смене пользователя состояние сообщений очищается; авторизация Apex не затрагивается.
- Единый преобразователь обрабатывает `not_authenticated`, `forbidden`, `session_not_found`, `invalid_client_key`, `invalid_message`, `invalid_limit`, `42501`, `anonymous_provider_disabled`, сеть, тайм-аут, Realtime, отсутствие/ошибку конфигурации и storage. Сырые SQL, stack, details и конфигурация Supabase не передаются как пользовательский текст и не логируются.

### Вопросы и блокеры интеграции

1. В текущем окружении не заданы `VITE_CHAT_SUPABASE_URL` и `VITE_CHAT_SUPABASE_PUBLISHABLE_KEY`. Перед реальным подключением нужны URL проекта Chat из контракта и его публичный publishable/anon key в локальном/сборочном окружении. Пока транспорт возвращает «Подключение к чату не настроено». Ключ не запрашивался и не копировался из Apex.
2. По поставленному backend-журналу Anonymous Sign-Ins были выключены. Текущее состояние не проверялось и не менялось. Владелец проекта должен подтвердить включение анонимного Auth; это блокирует интеграционный вход, но не локальные проверки.
3. Требуется отдельная разрешённая интеграционная проверка реального Auth, прав RPC и событий Realtime после настройки окружения. Успех моков не доказывает доступность сервера. Автоматические проверки не должны отправлять реальные сообщения.
4. Курсор истории `p_before` содержит только время. Совпадения `created_at` на границе страниц теоретически могут пропустить строки: `clock_timestamp()` не гарантирует уникальность. Для строгой гарантии полноты нужен подтверждённый серверный составной курсор; фронтенд не меняет контракт и базу.
5. Восстановление диалога зависит и от сохранённой Auth-сессии, и от `client_key`. После удаления Auth-хранилища новый анонимный пользователь не получает доступ к прежнему диалогу. Исходящий подготовленный объект пока хранится вызывающей стороной в памяти, без outbox между перезагрузками.
