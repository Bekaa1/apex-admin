# Транспорт Chat

Контракт сервера: [CHAT_BACKEND.md](CHAT_BACKEND.md). Виджет включён на публичных маршрутах. На административных и Auth-страницах он не монтируется; соединение Chat начинается только при первом открытии окна.

## Подключение

- Клиент: `src/lib/chatSupabase.ts`, типы: `src/lib/chat.database.types.ts`.
- Публичная точка входа: `src/chat/index.ts`, единый экземпляр `chatTransport`.
- В окружении сборки нужны `VITE_CHAT_SUPABASE_URL` и `VITE_CHAT_SUPABASE_PUBLISHABLE_KEY`. В `.env.example` оставлены только пустые переменные. Разрешён publishable либо legacy anon key. Привилегированный ключ нельзя помещать в публичное окружение сборки.
- Клиент создаётся лениво, отдельно от Apex. Auth: `persistSession: true`, `autoRefreshToken: true`, `detectSessionInUrl: false`, `storageKey: apex-chat-auth:v1`.

## Жизненный цикл будущего виджета

1. Подписаться через `chatTransport.subscribe(listener)`; читать неизменяемый снимок через `getSnapshot()`. Подходит для `useSyncExternalStore`.
2. В эффекте открытия вызвать `initialize()` и обработать отклонение Promise. Параллельные вызовы разделяют одну инициализацию. Повторный вызов при готовом соединении ничего не создаёт; после ошибки/обрыва пересоздаёт подключение, предварительно закрыв старое.
3. При размонтировании отписать listener и вызвать `dispose()`. Он отменяет запросы, исключает поздние события, удаляет Realtime-канал и Auth-listener. Сохранённая Auth-сессия и ключ диалога остаются для следующего открытия. В рамках страницы жизненным циклом единого экземпляра должен управлять один владелец.
4. Без сессии используется `signInAnonymously()`. Одновременный вход защищён общим Promise; при поддержке Web Locks инициализация также согласуется между вкладками.
5. `client_key` — UUID в `localStorage["apex-chat-client-key:v1"]`. Существующий корректный ключ переиспользуется; UUID диалога в localStorage не сохраняется. При недоступном storage инициализация останавливается.
6. После Auth вызывается `chat_get_or_create_session`, создаётся INSERT-подписка `public.chat_messages` с фильтром по диалогу. Настройка SDK `postgres_changes_options.wait: true` откладывает `SUBSCRIBED` до подтверждения подписки. Только затем читается история.

## Сообщения

`ChatMessage`: `id`, `sessionId`, `sender`, `body`, `clientMessageId`, `createdAt`. Отправитель проверяется по значениям `visitor | responder`. Неизвестные форматы не приводятся к допустимому типу молча.

Для новой попытки сообщения один раз вызвать `prepareMessage(text)`, сохранить полученный `OutgoingChatMessage` у вызывающей стороны и передать в `send(message)`. При сетевой ошибке повторить **`send` с тем же объектом**, а не `prepareMessage`. Текст обрезается по краям, проверяется диапазон 1–4000 Unicode-символов. Одновременная отправка одного ключа использует один Promise. Автоматические повторы RPC отключены, включая встроенный retry PostgREST.

`chat_send_message` возвращает UUID, а не строку сообщения. После подтверждения транспорт читает каноническое сообщение из истории; параллельное Realtime-событие объединяется с ним. Ошибка чтения после подтверждённой записи не превращает успешную отправку в неуспешную. Неизвестный результат сохраняет ключ у вызывающей стороны. Черновики исходящих сообщений пока не сохраняются между перезагрузками браузера.

История читается через `chat_list_messages`: `refreshHistory()` — актуализация; `loadOlder(oldest.createdAt, limit)` — старые записи, limit 1–200. Первичная загрузка содержит до 200 последних записей. После переподключения дочитываются страницы до последней успешной контрольной точки, в том числе если ранее диалог был пустым. Постоянного polling нет.

Единое хранилище объединяет сообщения сначала по `id`, затем по паре `sender + clientMessageId` внутри диалога. Одинаковый ключ посетителя и ответчика не объединяется. Сортировка: точное время с микросекундами, затем `id`. Время сообщения не создаётся на клиенте. Ошибки доступны через безопасный `ChatError`; исходные SQL, details и сообщения Supabase наружу не передаются. Смена пользователя или выход из Chat очищает состояние и закрывает подписку.

## Границы проверки

Проверки транспорта выполняются на моках в `tests/chat-transport.test.mjs`, поведения виджета — в `tests/chat-widget.test.mjs`. Генерация ответов, операторские функции и вызовы серверного ответа не реализованы. Во время тестов реальные Auth/RPC/Realtime не вызываются. Актуальные блокеры интеграции и результаты проверок записаны в `CHAT_PROGRESS.md`.

`p_before` в текущем контракте — исключительно timestamp. Если несколько сообщений имеют одинаковое время ровно на границе страницы, API не позволяет гарантированно дочитать оставшиеся строки с этим временем. `clock_timestamp()` уменьшает вероятность совпадения, но не обеспечивает уникальность. Транспорт не выдумывает дополнительный серверный курсор. Для полной гарантии нужен подтверждённый составной курсор сервера; миграции не менялись.

## Виджет

- `src/chat/widget/ChatRouteLayout.tsx` — единое подключение в корневом layout React Router; `routePolicy.ts` — единственная проверка видимости. Публичные ветки помечены `handle.publicChat: true`.
- Доступен на `/pricing`, `/stores`, `/how-it-works`, `/privacy`, `/offer`; правовые документы с `returnTo=/signup` исключены. Административные, auth-маршруты, кабинет, неизвестные маршруты и деревья без публичного handle не показывают чат. Корень `/` остаётся административным редиректом; публичный лендинг здесь не создавался.
- `ChatWidget.tsx` и CSS Module используют компоненты/токены Apex, светлую и тёмную темы, словари `chat.ru/kk/en.json`. Сообщения — обычный React-текст с переносами, без HTML/Markdown/преобразования ссылок.
- `controller.ts` хранит только состояние интерфейса, текст поля, локальные исходящие сообщения и счётчики. В нём нет RPC/Auth/Realtime-логики: все операции выполняет существующий `chatTransport`.
- Закрытие окна сохраняет подписку для непрочитанных ответов. Уход на исключённый маршрут размонтирует виджет и вызывает `dispose()`. Повторное открытие в рамках публичных маршрутов не создаёт ещё одну подписку.
- После отправки локальная строка имеет `sending`, `sent` или `failed`. Она объединяется с канонической по ID/ключу посетителя. Повтор сохраняет подготовленный объект. Пока отправка идёт, можно печатать следующий текст; подтверждение очищает поле только если этот текст не менялся.
- Ответы при закрытом окне увеличивают локальный счётчик; начальная история и подгруженные старые страницы его не увеличивают. Открытие прокручивает к концу и сбрасывает счётчик. Новые сообщения при чтении старых не перемещают пользователя и показывают кнопку перехода вниз.
- `ChatSnapshot.historyLoaded`, `hasOlderMessages`, `errorSource` позволяют различать загрузку истории, её границу и ошибки соединения/чтения/отправки. Начальная история — до 200 строк, кнопка старых сообщений читает не более 100 через `p_before` и сохраняет видимую строку как якорь прокрутки. Точное количество страниц не выдумывается.
- Исходящие локальные сообщения, непрочитанный счётчик и введённый текст остаются в памяти. Между полными перезагрузками их outbox не сохраняется. Виджет получает ответы исключительно из `responder`-сообщений транспорта.
