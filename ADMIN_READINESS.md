Типы не доказывают наличие этих функций в текущем окружении, разрешение их вызова и правильность серверной реализации.
- Поиск этих административных функций в исполняемом коде `src/` вне файла типов не дал совпадений. В собранном JS нет вызовов `is_apex_admin`, `admin_moderate_campaign`, `admin_mark_invoice_paid`.

### 2.4. Опасные операции

- **Модерация:** `admin_moderate_campaign` объявлена в типах, но не вызывается. Требование проведения модерации через этот RPC пока не реализовано.
- **Оплата:** `admin_mark_invoice_paid` объявлена в типах, но не вызывается. Подтверждение счёта не реализовано.
- **Прямые изменения:** в исполняемом клиентском коде не найдены прямые PostgREST `update/insert/upsert/delete`, меняющие статусы, бюджет или порции. Найденные одноимённые методы относятся к URL-фильтрам и коллекциям. `auth.updateUser` относится к пользовательским контактам, а не к статусам кампаний или счетов.
- **Существующие RPC:** создание и повторная отправка кампании выполняются через `submit_campaign` и `resubmit_campaign`; корпоративная заявка — через `submit_corporate_request`. Это операции рекламодателя, а не замена административных RPC.
- **Автоматические повторы:** в `src/lib/queryClient.ts` настроен повтор чтения, не мутаций. Установленная библиотека TanStack Query в `node_modules/@tanstack/query-core/src/mutation.ts` использует для мутаций `retry: this.options.retry ?? 0`. Переопределений повторов мутаций в приложении не найдено.
- **Ограничение:** поведение административной финансовой мутации после тайм-аута не проверено — такой мутации в интерфейсе нет. Идемпотентность и атомарность серверного подтверждения оплаты не подтверждены. Реальные операции не выполнялись.

Небольшие локальные исправления не вносились: найденные основные пробелы требуют разработки отсутствующих административных функций. Исходный APEX оставлен без изменений.

## 4. Неподтверждённые серверные права и бизнес-правила

Не подтверждены доступность и актуальность RPC из типов, результат `is_apex_admin` для разных пользователей, источник полномочий, права чтения всех клиентов/кампаний/счетов, серверные переходы статусов, однократность финансовых изменений, запись аудита и разрешения на удаление медиа.

Локальный API имитировал только ответы для проверки поведения клиента. Он не доказывает, что рабочий Supabase выдаёт или запрещает какие-либо данные. Готовность сервера по файлу типов или по успешному входу не заявляется.

### Функции, отложенные до подтверждения API

В журнале до этой проверки есть только подготовительный этап; ранее согласованного списка функций, отложенных именно из-за доказанного отсутствия серверного API, нет. На сервере отсутствие этих API не установлено.

В рамках данного аудита намеренно не разрабатывались административные списки и показатели, подтверждение оплаты, модерация, обработка корпоративных заявок, управление оборудованием, тарифами и очистка медиа. Для них нужно подтвердить контракт существующих PostgREST-эндпоинтов/RPC и права. Наличие типов для трёх `admin_*` функций и `is_apex_admin` зафиксировано отдельно; их нельзя считать отсутствующими или проверенными без исследования тестового сервера.

## 5. Необходимые действия бэкенд-разработчика

1. Предоставить отдельное тестовое окружение, синтетические данные и безопасный способ входа для существующих сценариев сотрудника и пользователя без полномочий. Учётные данные передавать отдельно от журналов. Рабочая база для приёмки не используется.
2. Подтвердить контракт и серверную реализацию `is_apex_admin`, источник полномочий и поведение при отсутствии сессии, отзыве полномочий и ошибке. Новые роли самостоятельно не вводить.
3. Подтвердить доступные источники общих списков и метрик, пагинацию, фильтры, разрешённые поля и ограничения. Использовать существующие представления/RPC, если они подходят; необходимость отдельного API-сервера не установлена.
4. Проверить серверную авторизацию внутри `admin_moderate_campaign` и `admin_mark_invoice_paid`, допустимые состояния, атомарность, конкурентные вызовы, однократность финансовых изменений и формат ошибок. Клиентская кнопка и `RequireAdmin` не заменяют эту защиту.
5. Уточнить контракт счетов, статусов корпоративных заявок, изменения тарифов и операций с оборудованием. Не выводить бизнес-правила из названий таблиц.
6. Подтвердить серверный аудит операций и права чтения `audit_log`.
7. Подтвердить `admin_campaign_media_orphans` и механизм очистки: повторная проверка использования файла непосредственно перед удалением, права Storage, защита от конкурентного появления ссылок. Способ удаления пока не согласован.
8. Предоставить воспроизводимые миграции/документацию RLS и RPC, затем актуальные сгенерированные типы. Текущие типы вручную не исправлялись.

Все пункты этого раздела — необходимые последующие действия, а не изменения, выполненные в рамках проверки.

## 6. Необходимые настройки нового домена

Конкретное имя домена и целевой сервер для ApexAdmin не переданы. Никакие DNS-записи, сертификаты, настройки Caddy/Nginx, Supabase Auth или Storage не изменялись.

После отдельного согласования потребуется:

1. Указать точный FQDN и целевой хостинг; выделить независимый каталог/виртуальный хост административной панели без замены исходного сайта APEX.
2. Настроить подходящую DNS-запись на подтверждённый адрес сервера и HTTPS для нового имени. Конкретное значение записи сейчас не определено.
3. Настроить выдачу SPA: прямые административные URL должны возвращать `index.html`, статические файлы — корректные MIME-типы; HTML должен обновляться при выпуске новой версии.
4. Подтвердить окружение сборки и использовать только URL Supabase и публичный клиентский ключ. Серверные ключи в `VITE_*` недопустимы.
5. Согласовать разрешённые redirect URL и параметры Auth для нового origin. Если Supabase общий с исходным сайтом, сохранить нужные адреса исходного приложения и не менять глобальные настройки без анализа обоих приложений.
6. При наличии соответствующих ограничений согласовать CORS для вызываемых Edge Functions и политику CSP. Не считать текущий общий доступ к Storage основанием для расширения прав.
7. Выполнить приёмку на отдельном тестовом домене до согласования production-публикации, включая прямые URL, сессию после обновления страницы и отказ пользователю без полномочий.

## 7. Сценарии приёмки на тестовых данных

Эти сценарии задают критерии последующей приёмки; **они не отмечены как выполненные**. Для них сначала нужны административная реализация и отдельное тестовое окружение.

| № | Сценарий | Ожидаемое подтверждение |
| --- | --- | --- |
| 1 | Прямой URL каждого списка и карточки без сессии | Доступ закрыт; общие административные запросы не отправляются |
| 2 | Пользователь без полномочий; `is_apex_admin` возвращает `false` | Экран отказа; ни один административный запрос и элемент опасного действия недоступен |
| 3 | Ошибка/тайм-аут проверки администратора | Доступ остаётся закрытым; нет перехода в разрешённое состояние по умолчанию |
| 4 | Подтверждённый сотрудник открывает каждый раздел | Только после успешной проверки прав отправляются разрешённые запросы; список, карточка, фильтры и пагинация работают |
| 5 | Выход, смена пользователя, отзыв полномочий во время запроса | Кэш очищается/изолируется; поздний ответ предыдущего пользователя не появляется; прямой URL повторно проверяет доступ |
| 6 | Одобрение и отклонение синтетической кампании | Используется только `admin_moderate_campaign`; допустимые причины/комментарии, итоговый статус и аудит соответствуют серверному контракту |
| 7 | Синтетический счёт: двойное нажатие, повторный запрос, потеря ответа и конкурентная оплата | Используется только `admin_mark_invoice_paid`; автоматических повторов финансовой мутации нет; нет двойного изменения бюджета или порций; итог проверяется чтением |
| 8 | Общие показатели и списки для нескольких синтетических клиентов | Источник возвращает подтверждённый административный охват, а не персональные `my_*` данные; права отдельно проверены для сотрудника и обычного пользователя |
| 9 | Магазины, зоны, тележки, маячки, тарифы и корпоративные заявки | Операции, связи, ограничения и статусы соответствуют согласованному контракту; ошибки не скрываются |
| 10 | Неиспользуемые медиа: файл используется перед удалением, удаление запрещено, файл отсутствует | Система повторно проверяет использование и права; действующее медиа не удаляется; действие отражается в журнале |
| 11 | Loading/empty/error, 1440 и 390, клавиатура, обе темы | Проверен каждый реализованный административный экран, а не только общая оболочка |
| 12 | Выпуск на согласованный тестовый домен | HTTPS, прямые URL, перезагрузка, сессия, recovery/redirect-сценарии, свежесть HTML и отсутствие серверных секретов подтверждены |

До закрытия блокеров этот отчёт не является разрешением на production-запуск.
