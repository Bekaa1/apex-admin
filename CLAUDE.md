# Apex Web

Веб Apexmedia для рекламодателей: лендинг, авторизация и личный кабинет. Apexmedia показывает 7-секундную видеорекламу на планшетах, закреплённых на тележках в супермаркетах Казахстана. Рекламодатель выбирает магазины и зоны полок, пополняет баланс и смотрит статистику показов.

Срок на весь веб — 3–4 дня (до ~09–10.10.2026). Тестов нет: работаем быстро, но код остаётся чистым и предсказуемым.

Команда:
- Фронтенд на React делаем вдвоём. Каждый верстает свои экраны и сам пишет для них API (`api.ts`, `useXxx.ts`).
  - Мы — пользователь и Claude Code. Рисуем страницы в Claude Design и верстаем их. Наша зона: каркас кабинета (меню слева, навигация, роутинг, сессия), главная кабинета и часть разделов.
  - `Bekaa1` работает через три агента Codex: ветки `agent/1–3`, worktree, правила в `AGENTS.md`. Его зона: авторизация и лендинг (уже сделаны) и остальные разделы кабинета после мержа каркаса.
- Бэкенд (Supabase) ведёт третий разработчик со своим ИИ. Мы и `Bekaa1` Supabase только читаем.
- В кабинете около 5 разделов. Каждый раздел целиком принадлежит одному владельцу: экраны, тексты и API.
- Пересекаемся только через `main`.

## Работа со мной
- Отвечать на русском и кратко.
- Не придумывать экраны, тексты и бизнес-правила, которых нет. Спросить или собрать экран из имеющихся элементов, а недостающее перечислить в «Design gaps».
- Сообщение «Фича: …» начинает новый цикл: ветка → работа → PR (см. «Процесс»).
- Комментарии в коде пишем только там, где без них неясно «почему»: обход бага, внешнее ограничение, неочевидное решение. Очевидное не комментируем.

## Стек
- React 19, TypeScript 6 (`strict` включён по умолчанию), Vite 8, npm. `package-lock.json` хранится в git. Нужен Node 20.19+.
- Линтер — oxlint (`.oxlintrc.json`, дизайн-кит исключён из проверки).
- Бэкенд — Supabase Cloud (supabase.com): Auth, Postgres + RLS, `@supabase/supabase-js` v2. Я подключаюсь к нему через коннектор Supabase в claude.ai и только читаю (см. «Supabase»).
- Шрифты — локальные TTF из `src/assets/fonts`, подключены в `design-system/fonts.css`.
- Tailwind и сторонние UI-киты не используем: только компоненты и токены дизайн-кита.
- Маршруты — `react-router` v7 (v8 требует Node 22.22+). Серверные данные — `@tanstack/react-query` v5. Оба согласованы с `Bekaa1`. Новые зависимости добавляем только после согласования с ним.

## Команды
- `npm run dev` — запуск на http://localhost:5173
- `npm run lint` — oxlint
- `npm run build` — `tsc -b` и сборка, это же проверка типов

## Архитектура
Структура повторяет дизайн-кит, и агенты Codex уже работают по ней. Существующие папки не переносим: переезд даст конфликты с их ветками. Новый код добавляем в том же стиле.

```
src/
  main.tsx              провайдеры (react-query, тема, язык, сессия), глобальные стили
  App.tsx, routes.tsx   RouterProvider; все маршруты, кабинетные строятся из cabinet/sections.ts
  auth/AuthRoutes.tsx   реальные OTP/сброс пароля; contact/channel/purpose передаются через состояние react-router
  design-system/        компоненты и токены кита; правим только вместе с китом
  i18n/                 I18nProvider и словари <раздел>.{ru,kk,en}.json с одинаковыми ключами; новый файл подхватывается сам
  auth/                 авторизация, AuthSessionProvider, RequireSession, вход по почте или казахстанскому номеру
  landing/              лендинг
  cabinet/              кабинет рекламодателя
    CabinetLayout.tsx     каркас: SideNav (меню → рейка ≤1100px), TopBar, TabBar (телефон ≤760px)
    sections.ts           разделы: путь, ключ названия, иконка, lazy-страница, подстраницы; CABINET_LINKS — адреса
    campaignStatus.ts     статусы кампаний → цвет бейджа, подписи в cabinet.status.*
    campaignBudget.ts, plays.ts, stores.ts, tariffs.ts, queryKeys.ts — общее для разделов: бюджет, показы,
                          «Все магазины», тарифы по дизайну (тексты в cabinet.tariffs.*), ключи react-query
    cabinet.css           общий слой кабинета из дизайна (cab-): каркас, карточки, таблица, KPI, чек, тарифы
    ui/ButtonLink.tsx     ссылка роутера в виде кнопки кита (Button с href перезагружает страницу)
    ui/LoadError.tsx      «Не удалось загрузить» с кнопкой «Повторить»
    demo.ts               ?demo=new|active|loading|error — превью состояний, только в dev
    home/                 главная: model.ts (строки вью → данные экрана), useHomeState, гид и сводка
    campaigns/            «Мои кампании»: список (list/), стили cmp- в campaigns.css; фильтры в URL
      wizard/               мастер «Новая кампания»: шаг в ?step=, форма в useReducer и sessionStorage вкладки
      corporate/            корпоративный тариф
    <раздел>/             остальные разделы
      XxxPage.tsx           страница раздела: подключает данные
      Xxx*.tsx              презентационные компоненты: props → UI
      Xxx.module.css        стили
      api.ts                запросы раздела к Supabase
      useXxx.ts             хуки (react-query)
  lib/                  format.ts (деньги, числа, %, списки, plural, даты), contacts.ts, queryClient.ts;
                        supabase.ts — общий типизированный клиент, allRows (чтение постранично) и uploadToStorage (загрузка с прогрессом),
                        database.types.ts — сгенерированные типы,
                        dates.ts — даты по Алматы
  assets/               шрифты и картинки
```

- Новый раздел — это папка `src/cabinet/<раздел>/` и одна запись в `sections.ts` (`page`, при необходимости `subpages`). Раздел без `page` показывает пустую заглушку. Тексты раздела лежат в `src/i18n/<раздел>.{ru,kk,en}.json`.

- Экран — презентационный компонент, как экраны кита. Данные подключает хук раздела, запросы живут только в `api.ts`.
- Разделы не импортируют друг друга. Общее для кабинета кладём в `cabinet/`, базовые UI-компоненты — в `design-system/` (только по ките), утилиты — в `lib/`.
- Импорты относительные, как в ките.
- `App.tsx`, `main.tsx`, `index.css`, конфиги и `package.json` правят и агенты Codex. Изменения в них делаем маленькими отдельными коммитами и согласовываем.
- Кабинет живёт под `/cabinet`. Неизвестный адрес внутри кабинета ведёт на `/cabinet`, вне кабинета — на лендинг. Ссылки внутри приложения — `Link`, `NavLink` или `ButtonLink`, обычный `<a>` перезагружает страницу.

## Паттерны React
- Компоненты — функции с именованным экспортом (кроме `App`). Компонент — `PascalCase.tsx`, хук — `useSomething.ts`.
- Отображение отделено от данных. Презентационный компонент получает props и отдаёт события через колбэки, данные подключают хуки.
- Данные с сервера не дублируем в нескольких `useState`: один источник — хук или кэш запросов. Сессия — в одном провайдере, состояние интерфейса — локально в компоненте. Глобальный стор без явной нужды не заводим.
- Производные значения вычисляем при рендере, а не через `useEffect` + `useState`. `useEffect` нужен только для синхронизации с внешним миром.
- Состояния экрана обрабатываем ранними `return` в порядке loading → error → empty → данные.
- Компонент держим примерно до 150 строк. Если он растёт, выносим части в подкомпоненты, а логику — в хуки.
- Типы строгие: без `any`, без лишних `as` и `!`. Состояния описываем размеченными объединениями.
- Код, который повторяется два раза и больше, выносим в общее место (см. «Архитектура»).

- Стили пишем только на токенах (`var(--…)` из `tokens.css`). Свои hex, размеры шрифтов, радиусы и тени запрещены. Шрифты: Geologica для заголовков и цифр, Onest для текста. Inter, Manrope и Unbounded не используем.

  - экраны, перенесённые из Claude Design один в один, держат глобальный префикс: `ax-` (кит), `auth…`, `land…`, `cab-` (кабинет), `cmp-` (кампании);

- На экране одна primary-кнопка. Ошибку поля показываем у поля, ошибку формы — в Alert. Фокус с клавиатуры виден, тап-зоны не меньше 44px.
- Если в ките нет нужного цвета или компонента, новый не придумываем: берём ближайший из кита и записываем в «Design gaps». Новые токены и компоненты сначала добавляет в дизайн-систему владелец дизайна, затем они появляются в коде.
- Claude Design может ошибаться. Где дизайн расходится с китом (тап-зоны 44px, шкала шрифтов, токены), делаем по киту. Недостающие по дизайну состояния и тексты (ошибки, пустые состояния) дописываем по правилам кита и перечисляем в PR.
- Числа и деньги форматируем так: «12 500 ₸», «7 сек». Только через `lib/format.ts`. У браузеров нет казахских данных для чисел, поэтому kk берёт формат ru-RU.

## Supabase
- Бэкенд ведёт третий разработчик со своим ИИ, это не `Bekaa1`. Мы бэкенд изучаем, но не меняем.
- **Без точной и конкретной просьбы пользователя в Supabase ничего не меняем.**
  - Запрет касается схемы, данных, RLS, функций и триггеров, Edge Functions, Auth, Storage, настроек проекта, веток, pause/restore и любых платных действий.
  - Общее «да» или «делай» разрешением не считается: нужна просьба про конкретное изменение.
- Через MCP только читаем: `list_*`, `get_*`, `search_docs`, `generate_typescript_types`, логи, advisors. `execute_sql` — только `SELECT`. Персональные данные без нужды не читаем.
- Проекты в организации Apex:
  - «Apex» (`eveylcsziemhqouazebu`) — основной бэкенд;
  - «Cart» (`yasoadhyjmstegjhcdzi`) — бэкенд планшетов, раз в час синхронизируется в «Apex».
- Что важно фронту (снимок на 06.10, подробности в session-log):
  - Данные кабинета берём только из `my_*` вью: `my_ad_stats_summary`, `my_campaigns_stats`, `my_daily_plays*`, `my_campaign_store_shares`, `my_campaign_zone_shares`. Они фильтруют по `auth.uid()`.
  - Вью `advertiser_*`, `ad_campaign_stats`, `user_ad_stats`, `all_*`, `partner_*` и похожие не используем: они отдают данные всех пользователей.
  - По RLS сейчас видны все строки `ads`, поэтому запросы к `ads` всегда фильтруем по `user_id` текущего пользователя.
  - Профиль — `public.users` (1:1 к `auth.users`). Текущая регистрация сохраняет его через RPC `complete_signup_profile(p_full_name, p_bin, p_company_name)`.
  - Статистика приходит из «Cart» раз в час, поэтому возможна задержка до часа.
- Если фронту нужна правка бэкенда, пишу запрос для бэкенд-разработчика: что нужно, для какого экрана, предлагаемый SQL/RLS, насколько срочно.
  - Пользователь пересылает запрос, копия идёт в session-log в запись фичи.
  - Пока правку не сделали, работаем на том, что есть, или на моках и пишем об этом в PR.
- Клиент один: `src/lib/supabase.ts`. Он типизирован `Database` из `src/lib/database.types.ts`. Типы строк берём через `Tables<'…'>` и `Database['public']['Views'][…]`, своих копий не пишем.
  - Этот файл генерируется через MCP `generate_typescript_types`. Руками его не правим.
  - После изменений бэкенда генерируем заново.
- Ключи храним только в `.env.local` (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`). В git лежит `.env.example` с шаблонными значениями. Во фронте используем только anon (publishable) ключ; service_role и secret сюда не попадают никогда.
- Данные защищает RLS, а не фронт. Фильтр по `user_id` на клиенте нужен только для отображения, безопасности он не даёт. Компоненты не обращаются к Supabase напрямую, только через `api.ts`.
- Данные пользователя читаем только при активной сессии: хуки запросов включаются, когда сессия есть. `/cabinet/*` защищён `RequireSession`; выход завершает текущую сессию Supabase и очищает кэш react-query. Блок аккаунта читает только свой `public.users.company_name` через `cabinet/api.ts`. Главная читает данные через `cabinet/home/api.ts`: `my_campaigns_stats`, `my_daily_plays_by_campaign` (14 дней), свои строки `ads` (обложка, магазин) и `stores`. Список кампаний — через `cabinet/campaigns/api.ts`: то же, показы за 30 дней. Все списки читаются через `allRows`. Мастер кампании читает `stores` и `zones`, для «Повторить» и «Исправить» — свою строку `ads` и её `ad_zones`; ролики и обложки грузит в бакет `documents` (`campaigns/<uid>/…`). В `ads` мастер ничего не пишет: отправка включится с RPC `submit_campaign`. `?demo=` доступен только в dev после входа.

## Процесс (git)
- Одна фича — одна ветка от свежего `main`: `feature/<коротко>`, для исправлений `fix/…`, для служебных задач `chore/…`. Отдельной ветки «claude» нет. В `main` напрямую не коммитим. Ветки `agent/*` и worktree второго разработчика не трогаем.
- Начало: `git switch main && git pull && git switch -c feature/<имя>`. Рабочее дерево перед этим чистое.
- Обновить ветку из `main`: `git fetch origin && git merge origin/main`.
- После каждого изменения запускаем `npm run lint` и `npm run build`. Интерфейс смотрим во встроенном браузере (dev-сервер из `.claude/launch.json`) и сверяем с дизайном.
- Завершение фичи:
  1. запись в `session-log.md`;
  2. коммит в стиле Conventional Commits на английском (`feat: …`, `fix: …`, `chore: …`);
  3. push;
  4. PR в `main` с кратким описанием на русском: что сделано, как проверено, какие design gaps.
- PR открываю после каждой фичи, если пользователь не попросил подождать. Смотрит и мёрджит его пользователь через «Squash and merge».
- Коммитим только файлы своей фичи. Секреты (`.env*`, ключи) в git не попадают.
