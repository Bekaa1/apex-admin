# Роли ApexAdmin

Дата: 08.10.2026. Ветка: `fix/bekzhan-1-5-7-10-12-13`.

Основание: предоставленные `Роли, тарифы, лимиты — техдок.docx` и
`roles_tariffs_limits.zip`, включая SQL `staff_roles_v2` и актуальные типы.
Решение пользователя: директор и маркетолог видят **все магазины своей сети**.
Чужие сети в их интерфейс не включаются. Счета модератору закрыты по отдельному
указанию пользователя; серверная политика исправлена 08.10.2026 (см. ниже).

## Определение доступа

- Один существующий `RequireAdmin`, клиент Apex и `AuthSessionProvider`.
- Вход в панель теперь определяется `my_roles()`: `is_apex_admin()` не подходит
  для бухгалтера, модератора и других сотрудников.
- `src/auth/permissions.ts` содержит роли, разрешения, стартовую страницу и
  соответствие разделов разрешениям. Неизвестные роли не дают прав.
- До завершения проверки страницы с административными запросами не монтируются.
  Ошибка, некорректный ответ, отсутствие RPC/конфигурации закрывают доступ.
- Маршруты получают `handle.adminPermission`. `RequireAdminSection` проверяет
  реально сопоставленный маршрут через `useMatches`, включая адреса с другим
  регистром и кодированием символов. Меню использует те же разрешения.
- При проверке прав административные данные сбрасываются: привязка к сети может
  измениться без изменения названий ролей. Сохраняются только флаги незавершённых
  финансовых/статусных операций, чтобы не разрешить слепой повтор. Выход и смена
  пользователя очищают весь кэш существующим провайдером сессии.
- Права складываются при нескольких ролях. Например, `moderator + accountant`
  получает счета именно благодаря роли `accountant`.

## Матрица интерфейса

| Роль | Разделы и действия |
| --- | --- |
| `admin`, `owner` | Все существующие административные разделы, команда и сети. Публикация магазина дополнительно требует `is_apex_store_owner() === true`. |
| `accountant` | Обзор, кампании, клиенты, магазины без оборудования, тарифы и их история, счета: подтверждение оплаты и отмена неоплаченного счёта. Нет модерации, управления ролями и изменения тарифов. |
| `moderator` | Обзор, кампании, модерация, пауза/возобновление, клиенты, магазины без оборудования, корпоративные заявки, неиспользуемые медиа. Нет счетов, их счётчиков и вложенных финансовых списков. |
| `manager` | Магазины, зоны, тележки, маячки, заявки на магазины, маршруты тележек. Нет общих кампаний, клиентов и счетов. |
| `director`, `marketer` | Магазины своей сети, кампании в них, Smart тележки, статусы и маршруты. Только просмотр; без общих административных списков и решений. |
| `client` | Не получает доступ к `/admin`. Существующий рекламодательский кабинет сохранён. |

Статусы кампании, её бюджет/расход остаются видимыми разрешённым читателям
кампаний. Это отдельные поля кампании; запросы к счетам и порциям бюджета у
модератора не запускаются. В клиентской карточке URL вкладки счетов также защищён.
В магазине URL вкладки оборудования не обходит права.

## Маршруты

- `/admin/team` — команда, выдача/снятие роли, создание сети, привязка её
  сотрудников и магазинов. Только `admin`/`owner`.
- `/admin/partner/stores` и `/admin/partner/stores/:id` — магазины своей сети.
- `/admin/partner/campaigns` — кампании сети, без перехода в общую карточку.
- `/admin/partner/equipment` — Smart тележки сети.
- `/admin/cart-routes/:id` — посещения зон по событиям показов, период до 31 дня
  в Asia/Almaty. Это не непрерывное отслеживание перемещений. Сервер ограничивает
  выдачу 5000 строками; интерфейс сообщает это, страницы локальные по 25 записей.
- Существующие `/admin/campaigns/:id`, `/admin/invoices/:id`, `/admin/tariffs`
  дополнены разрешёнными действиями и историей.

Сотрудники используют административную сборку (`adminapex.kz`). Публичный сайт
и кабинет рекламодателя продолжают собираться отдельно.

## Источники и операции

- Права: `my_roles`, отдельно существующий `is_apex_store_owner`.
- Команда: `admin_list_team`, серверная пагинация 25 + одна строка для «Далее».
  Поиск кандидатов — `users`, сетей — `partners`, магазинов — `stores`, до 25
  результатов, после явного поиска. Значения экранируются для PostgREST/regex.
- Изменения: `admin_set_user_role`, `admin_save_partner`,
  `admin_set_partner_member`, `admin_set_store_partner`. Нет прямой записи в
  `users`, `user_roles`, `partners` или `stores`.
- Своя сеть: `current_partner_id`, `partner_stores`, `partner_campaign_view`,
  `partner_devices`; серверная пагинация 25 + одна строка. Карточка дополнительно
  проверяет `stores.id` и `stores.partner_id` до запроса оборудования.
- Маршрут: `cart_route`; авторизация на конкретную тележку остаётся на сервере.
- Модерация/оплата: существующие `admin_moderate_campaign` и
  `admin_mark_invoice_paid` с проверкой соответствующего разрешения перед вызовом.
- Пауза: `admin_set_campaign_paused`, только из `active`/`paused`.
- Отмена: `admin_cancel_invoice`, только для `unpaid`. Общая блокировка интерфейса
  не позволяет одновременно открыть оплату и отмену.
- История: `admin_tariff_history`, до 50 изменений выбранного тарифа. JSON
  выводится обычным текстом в ограниченном прокручиваемом блоке.

Мутации требуют подтверждения, блокируют повторный клик и не повторяются
автоматически. Строковый результат не подставляется в статус: запись
перечитывается. После неизвестного результата паузы/отмены выполняется только
чтение; старый статус не считается доказательством невыполненной операции.
Блокировка интерфейса не заменяет серверную защиту от конкурентных действий.
При неизвестном результате создания сети требуется ручная проверка по названию;
RPC не имеет клиентского ключа идемпотентности.

В типах из архива уточнены подтверждённые SQL nullable-аргументы:
`admin_save_partner.p_id`, `admin_set_partner_member.p_partner_id/p_role`,
`admin_set_store_partner.p_partner_id`. Остальные существующие типы сохранены.

## Проверки и границы результата

- `npx tsc -b` — успешно после исправления несовместимости типа вкладки и
  объявления класса ошибки; позднейшие изменения также проверены обеими сборками.
- `npm run lint` — exit 0, восемь прежних предупреждений, новых нет.
- `npm run build` и `npm run build:admin` — exit 0; предупреждение Vite о чанках
  больше 500 kB сохраняется.
- `git diff --check` — успешно.
- Перед интеграцией выполнены 253/253 существующих и дополненных локальных
  теста без production-мутаций, включая матрицу ролей и защиту вложенных маршрутов.
  После деплоя браузер подтвердил загрузку обзора через my_roles с существующей
  сессией; console errors не было. Это не сквозной вход каждой отдельной ролью.
- Исходная проверка frontend не изменяла production. Затем по отдельному
  поручению исправлена одна политика RLS (ниже); бизнес-данные не менялись.
  Результаты интеграции и публикации фиксируются отдельно в ADMIN_PROGRESS.md.

## Серверные зависимости

1. **Запрет чтения чужих счетов модератором исправлен в Apex production** по явному
   поручению пользователя от 08.10.2026. Применена только миграция
   `20261008122030_restrict_staff_invoice_read.sql`: `staff_read_invoices`
   теперь требует `has_role('accountant')`. Остальные две политики сохранены:
   административная `is_apex_admin()` и чтение собственных счетов по `auth.uid()`.
   Фактическое состояние проверено в SQL Editor по `pg_policies`. По определениям
   `has_role`/`is_apex_admin` доступ admin/owner и сочетания ролей сохранён.
   Каталог зависимых представлений и функций проверен: `my_campaigns_stats`
   ограничен собственным user_id; RPC оплаты и отмены требуют accountant;
   submit/extend ограничены собственной кампанией. Проверка выполнена без
   чтения счетов клиентов и без финансовых операций. Сквозной вход под отдельной
   учётной записью модератора не выполнялся. Каталог миграций смешивает Apex/Chat,
   поэтому общий `db push` не запускался; SQL применён адресно через SQL Editor.
2. По документу сетей и назначений ролей ещё не было. Для реального использования
   требуется отдельно согласованное назначение сотрудников и привязка магазинов.
   Текущее состояние production в этой задаче не проверялось.
3. Проверить реальный доступ для каждой роли, изоляцию двух сетей, потерю роли во
   второй вкладке, права чтения профилей, RPC мутаций и историю тарифов на
   согласованных учётных записях. Описанные в техдоке проверки бэкенда не являются
   результатами этой локальной проверки фронтенда.
4. Каталог `stores/zones/beacons` по контракту доступен вошедшим пользователям для
   выбора рекламных площадок. Ограничение кабинета директора своей сетью не
   изменяет этот общий серверный каталог.
5. Отдельного staging в проекте не заявлено. Мутации в production нельзя
   использовать как автоматический smoke-тест.

Изменение тарифов, медиатребований и дневных лимитов — отдельные пункты техдока,
они не реализовывались в рамках правки ролей.
