# Добавление магазина в ApexAdmin

Актуальность: 8 октября 2026. Фронтенд проверен локально с подменённым API. Реальные права, транзакции и публикация в Supabase этой проверкой не подтверждены.

## Маршруты и навигация

| Маршрут | Назначение |
|---|---|
| `/admin/stores` | Реестр магазинов; переход к заявкам и созданию |
| `/admin/store-requests` | Список заявок, фильтр статуса, локальный поиск и продолжение черновика |
| `/admin/stores/new?step=details` | Новая заявка, без создания записи при открытии |
| `/admin/stores/new/:requestId?step=details` | Данные существующей заявки |
| `/admin/stores/new/:requestId?step=plan` | JSON-картограмма |
| `/admin/stores/new/:requestId?step=zoning` | Зоны и назначения элементов |
| `/admin/stores/new/:requestId?step=review` | Проверка, отправка и просмотр статуса |
| `/admin/store-requests/pending` | Очередь владельца |
| `/admin/store-requests/:requestId/review` | Рассмотрение владельцем |
| `/admin/stores/:id` | Карточка опубликованного магазина |

Маршруты определены один раз в `src/routes.tsx`. UUID заявки хранится в pathname, шаг — в `step`. Нет второго мастера или конкурирующего маршрута. Пункт «Заявки на магазины» расположен рядом с «Магазины»; на странице списка владельцу доступен переход «Ожидают решения».

Для собственной `inactive`/`rejected` заявки «Продолжить» выбирает первый незавершённый этап: незаполненные название/город/адрес → данные; нет плана → картограмма; нет зон → зонирование; иначе → проверка. Чужая заявка и `pending_owner_approval` открываются на просмотр. `approved` с `published_store_id` ведёт к магазину.

## Права и статусы

Все маршруты находятся под существующим `RequireAdmin`: отсутствие сессии ведёт на вход, только буквальный `is_apex_admin() === true` монтирует административные страницы. Ошибки, отсутствие конфигурации и отрицательный результат закрывают доступ.

Редактирование и отправка требуют одновременно `request.is_mine === true` и статуса `inactive` либо `rejected`. Проверка действует и в обработчиках операций. После отклонения показывается `review_comment`. Чужие заявки, `pending_owner_approval` и `approved` доступны только для чтения; ссылки исправления скрыты также у незавершённых чужих заявок.

Очередь и рассмотрение дополнительно защищены `RequireStoreOwner` и общим `useStoreOwnerAccess`, который вызывает `is_apex_store_owner()` и принимает только `true`. `users.role` не используется. Кнопки решений доступны только владельцу для `pending_owner_approval`. Рассмотрение владельца принудительно работает без редактирования даже для собственной заявки.

Текущий административный каркас требует от аккаунта владельца **обеих** проверок: `is_apex_admin` и `is_apex_store_owner`. Фактическую настройку такого аккаунта нужно подтвердить отдельно. Кэш прав и данных очищается существующим слоем сессии при выходе/смене пользователя.

| Статус | Поведение |
|---|---|
| `inactive` | Собственный редактируемый черновик |
| `rejected` | Комментарий владельца, исправление автором, повторная отправка |
| `pending_owner_approval` | Редактирование закрыто, дата отправки, ожидание решения |
| `approved` | Просмотр и ссылка на `published_store_id` |

Неизвестный статус не даёт права на изменение.

## Данные и RPC

Общий адаптер: `src/admin/stores/onboarding/api.ts` (`readResult`, `getRequest`), нормализация полной заявки — `onboarding/model.ts`; списков — `requests/model.ts`, очередь переиспользует этот адаптер. Runtime `null` не считается корректной непустой строкой только на основании сгенерированного TypeScript-типа.

| RPC | Использование |
|---|---|
| `admin_create_store_request` | Создание при явном сохранении; возвращает UUID |
| `admin_update_store_request` | Полный набор полей первого шага и ожидаемая revision |
| `admin_save_store_plan` | План и исходное имя JSON-файла |
| `admin_replace_store_zoning` | Все зоны и назначения одним атомарным запросом |
| `admin_submit_store_request` | Отправка после подтверждения |
| `admin_list_store_requests` | Список, `p_status` либо пустые аргументы |
| `get_store_request` | Загрузка и сверка результата операций |
| `is_apex_store_owner` | Право владельца, без аргументов |
| `owner_list_pending_store_requests` | Очередь, без аргументов |
| `owner_approve_store_request` | Публикация; возвращает UUID магазина |
| `owner_reject_store_request` | Отклонение с trim-комментарием 3–1000 символов |
| `get_store_plan` | Есть в установленном контракте; мастер его не вызывает, план берётся из `get_store_request` |

Процесс не вызывает `_store_*`, не записывает напрямую в `stores`, `zones`, заявки, планы, назначения или владельцев. Существующий реестр/карточка опубликованного магазина читают таблицы через свой прежний слой API.

Поле партнёра в мастере скрыто. `p_partner_id` опущен в create/update, поскольку актуальный тип допускает необязательный `string`, но не явный `null`; SQL default по контракту равен `NULL`.

Списки получают один ответ RPC, поиск и страницы по 25 строк применяются к загруженным данным. Фильтры хранятся в URL. Есть ручное обновление и перечитывание после возврата; polling отсутствует. Полученный ответ не объявляется полным реестром. Для больших объёмов нужно подтвердить серверные лимиты и согласовать серверную пагинацию.

## Четыре шага

1. **Данные магазина:** trim; название 2–120 символов, город до 80, адрес до 200, обязательный часовой пояс, по умолчанию `Asia/Almaty`. Город/адрес обязательны для продолжения и отправки; неполный черновик можно сохранить. «Сохранить» остаётся на шаге, «Сохранить и продолжить» открывает план. Есть предупреждение о несохранённых полях.
2. **Картограмма:** только JSON до 512 КБ, имя до 255 символов; version=1, положительные размеры до 100000; 1–1000 элементов, до 2000 декораций, metadata-объект. Проверяются ID, виды, геометрия, границы и строки. SVG показывает геометрию и подписи, масштаб/вписывание; JSON не вставляется как HTML. PNG/PDF и редактирование геометрии не реализованы.
3. **Зонирование:** до 200 зон со стабильными `zone-<uuid>` client_id, названия 1–80 символов с уникальностью без регистра, цвет `#RRGGBB` (перед отправкой uppercase), описание до 300 символов. Есть выбор, кисть, область, ластик, порядок и подтверждение удаления. Назначения хранятся `Map<element_id, zone_client_id>`; восстановление выполняется через `zone_id → client_id`. Один элемент — одна зона; каждая зона должна иметь элемент, неназначенные элементы допустимы. Устаревшие назначения показываются предупреждением и не отправляются обратно.
4. **Проверка:** данные, план, зоны и статус; список проверок со ссылками исправления только для автора. Отправка требует явного диалога с предупреждением о production и блокировке редактирования. Успех отображается после перечитывания фактического статуса.

План и зонирование предупреждают при уходе с несохранёнными изменениями. Во время запросов блокируются повторные действия и уход из мастера. Сервер остаётся окончательным источником правил.

## Request key и revision

`onboarding/attempt.ts` хранит попытку в `sessionStorage` под ключом `apex-admin:store-create:v1:<userId>`, отдельно для пользователя и вкладки. `crypto.randomUUID()` вызывается один раз при первом сохранении; после неизвестного результата повтор использует прежний ключ и прежние поля. Открытие страницы ничего не создаёт.

После успешного создания сохраняется короткоживущая отметка с UUID заявки. Она удаляется только когда этот UUID оказался в маршруте. Если страница перезагрузилась между ответом и переходом, форма восстанавливает существующую заявку вместо нового create. Другая заявка получает новый ключ после завершения предыдущей попытки. Если sessionStorage недоступен, создание блокируется с ошибкой, чтобы не потерять ключ идемпотентности. Закрытие вкладки удаляет sessionStorage; сохранять ключ между разными вкладками/устройствами этот механизм не обещает.

Revision находится в нормализованной записи и кэше `['admin', 'store-request', userId, requestId]`; при открытии шага запись перечитывается. Create устанавливает локальную revision=1 и затем загружает запись. Остальные изменения отправляют `p_expected_revision`, сохраняют возвращённую revision. Одобрение возвращает UUID магазина; новую revision получают из перечитанной заявки. Статусы оптимистически не меняются.

Все мутации имеют `retry: false` и синхронную блокировку повторного клика. Автоматических повторных записей нет. При `revision_conflict` выполняется чтение, пользователь должен проверить актуальные данные заново.

| Неизвестный результат | Сверка перед возможным новым действием |
|---|---|
| Create | Ручной повтор с прежним request_key |
| Данные | revision+1 и совпадение полей |
| План | revision+1 и совпадение JSON |
| Зонирование | revision+1, тот же план, совпадение зон/назначений после нормализации |
| Отправка | `pending_owner_approval` и revision+1 |
| Одобрение | `approved` и `published_store_id`; если остался pending — только ручное новое подтверждение |
| Отклонение | `rejected`; при pending автоматического повтора нет |

Если сверочное чтение не удалось, новые записи блокируются до отдельной успешной проверки состояния. После решений обновляются запись, очередь и связанные кэши списков. Клиентская блокировка не заменяет серверные транзакции, идемпотентность и конкуренцию.

## Ошибки и безопасность

Единый `onboarding/errors.ts`: код бизнес-ошибки из `error.message`, SQLSTATE `42501` → forbidden, проверенный `hint` → поле. Поддержаны not_authenticated, forbidden, not_found, invalid_status, revision_conflict, invalid_store, invalid_plan, plan_too_large, too_many_elements, duplicate_element, invalid_zones, invalid_assignments, owner_not_configured, already_published.

`error.details` выводится обычным текстом только для P0001 и точного совпадения с перечнем проверенных статических сообщений установленного SQL-контракта. Неизвестные, динамические и внутренние сообщения не показываются. Пользователь получает безопасный перевод; журнал диагностики содержит только операцию, код и разрешённое имя поля, без SQL, stack trace, значений заявки, комментариев, ключей или токенов.

## Ограничения и оставшаяся интеграционная приёмка

- Staging отсутствует; backend доступен только в production. Реальные RPC, создание/отправка/решения и SQL в этой проверке не выполнялись.
- Без изолированного окружения нельзя безопасно подтвердить реальные права администратора/владельца, полноту списков, атомарную публикацию плана и зон, конкурентные решения разных сессий и серверную идемпотентность. Они описаны контрактом, но тестовый имитатор их не доказывает. Нужен staging или отдельно согласованный безопасный интеграционный стенд с тестовыми аккаунтами и данными.
- Источник партнёров пуст и закрыт RLS. Для выбора партнёра нужен отдельный подтверждённый backend-контракт.
- `20261007160000_store_onboarding_zoning_and_grants.sql` хранится в репозитории; по документации она применена вручную и отсутствует в истории Supabase. Автоматически применять повторно нельзя. Согласование истории выполняет backend-разработчик отдельно.
- Контракт, database.types.ts и три миграции сохранены без изменений. Архив и распаковка исключены из Git. Реальные заявки, Supabase, RLS, роли, функции и production не изменялись; публикация приложения не выполнялась.
